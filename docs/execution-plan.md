# طرح اجرایی سامانه جامع بیمارستان رازی تبریز

نسخه ۱ · ۱۴۰۵/۰۷/۲۲ (2026-10-14) · وضعیت: **پیش‌نویس، منتظر تأیید مالک پروژه**

این سند بر پایه شرح پروژه و گزارش بررسی کد فعلی ([razi-review-1.md](گزارش بررسی کد قبلی، در پوشه پروژه)) نوشته شده است. هیچ کدی هنوز تغییر نکرده است. هرجا چیزی «استنتاج» یا «پیشنهاد» است، همین را صریح گفته‌ام. بخش ۱۳ فهرست پرسش‌هایی است که پاسخ آن‌ها پیش از شروع توسعه لازم است.

## ۱. خلاصه تصمیم‌های پیشنهادی

| موضوع | پیشنهاد | دلیل |
|---|---|---|
| ساختار مخزن | یک مخزن (monorepo) با پوشه‌های `android/`، `backend/`، `admin-web/`، `docs/` | تغییر API و اپ در یک PR، یک CI، مدیریت ساده‌تر برای تیم کوچک |
| بک‌اند | یک «مونولیت ماژولار» با FastAPI (نه میکروسرویس) | تیم کوچک، استقرار ساده روی سرور بیمارستان؛ ماژول‌ها بعداً قابل جداسازی‌اند |
| اپ اندروید | از نو با Compose؛ کد XML فعلی فقط مرجع محتوا (سؤال‌های فرم خطا) | کد فعلی Activity‌محور است و Compose در آن استفاده نشده |
| یک اپ یا دو اپ | **یک اپ** با دو بخش جدا: «عمومی» بدون ورود، «کارکنان» پس از ورود | توزیع ساده‌تر؛ جداسازی واقعی در سمت سرور انجام می‌شود، نه در اپ |
| پنل مدیریت | React + TypeScript + Vite + Ant Design (پشتیبانی RTL و locale فارسی) | کتابخانه آماده جدول/فرم/نمودار با راست‌چین |
| دامنه MVP | ورود و نقش‌ها، ثبت و پیگیری خطا، اطلاعیه‌ها، درخواست‌های پشتیبانی، راهنمای عمومی و ثبت شکایت، داشبورد پایه | بیشترین ارزش با کمترین وابستگی به سامانه‌های بیرونی |
| خارج از MVP | نوبت‌دهی، پرونده بیمار، اتصال به HIS، گفتگو، آموزش و آزمون، پژوهش | وابسته به مجوز یا حجم بالا؛ در فازهای بعد |

## ۲. اصول طراحی

1. **تفکیک محیط عمومی و داخلی در سرور:** مسیرهای `/api/v1/public/*` (مراجعان) و `/api/v1/staff/*` (کارکنان) جدا هستند. در صورت امکان، بخش عمومی روی سرور/شبکه جدا (DMZ) و بخش کارکنان فقط از شبکه داخلی یا VPN در دسترس باشد (به پاسخ پرسش ۳ بستگی دارد).
2. **کنترل دسترسی فقط در سرور:** اپ و پنل فقط چیزی را نشان می‌دهند که سرور اجازه داده؛ هر endpoint مجوز مشخص دارد.
3. **کمترین داده بیمار:** در MVP هیچ اطلاعات پزشکی بیمار ذخیره نمی‌شود، جز شناسه‌های لازم در گزارش خطا (شماره پرونده، اختیاری) که رمزنگاری‌شده در پایگاه داده نگه داشته می‌شوند.
4. **حسابرسی:** هر مشاهده یا تغییر داده حساس (گزارش خطا، نقش‌ها، کاربران) در `audit_logs` ثبت می‌شود و قابل حذف از طریق برنامه نیست.
5. **فرم‌های پویا:** فرم ثبت خطا و انواع درخواست‌ها از روی «قالب فرم» نسخه‌دار ساخته می‌شوند تا مسئول ایمنی بیمار بدون انتشار نسخه جدید اپ بتواند سؤال‌ها را تغییر دهد.
6. **فارسی و راست‌چین کامل:** تاریخ شمسی در همه رابط‌ها (ذخیره در سرور به UTC)، فونت Vazirmatn (مجوز OFL)، اعداد فارسی در نمایش.
7. **آفلاین در حد لازم:** گزارش خطا و درخواست‌ها در صورت قطع شبکه در صف محلی می‌مانند و بعداً ارسال می‌شوند.

## ۳. نقش‌ها و سطوح دسترسی

مدل: **RBAC با دامنه واحد**. هر کاربر می‌تواند چند نقش داشته باشد و هر نقش می‌تواند به یک واحد (بخش) محدود شود. مجوزها به شکل `ماژول.عمل.دامنه` تعریف می‌شوند، مثلاً `incident.read.unit` یا `incident.read.all`.

| نقش | کاربر نمونه | دسترسی اصلی |
|---|---|---|
| مهمان | هر کسی بدون ورود | راهنمای بخش‌ها، پرسش‌های متداول، اطلاعیه‌های عمومی، ثبت شکایت/پیشنهاد (با کد پیگیری) |
| مراجع ثبت‌نام‌شده | بیمار، همراه | موارد مهمان + پیگیری درخواست‌ها و شکایت‌های خود، نظرسنجی (فاز ۵؛ نیاز به OTP پیامکی) |
| کارمند | پرستار، پزشک، کارشناس، خدمات | ثبت و پیگیری گزارش خطای خود، اطلاعیه‌ها، درخواست پشتیبانی، (بعداً) آموزش و گفتگو |
| دانشجو/دستیار | دستیار تخصصی، دانشجو | مثل کارمند، با دسترسی محدودتر و دوره‌های ویژه |
| مسئول واحد | سرپرستار، مدیر بخش | مشاهده گزارش‌ها و درخواست‌های واحد خود، ثبت اقدام |
| کارشناس ایمنی بیمار | دفتر بهبود کیفیت / ایمنی بیمار | دریافت، ارجاع و بستن همه گزارش‌های خطا، اقدام اصلاحی، آمار |
| کارشناس پشتیبانی | فناوری اطلاعات، تجهیزات پزشکی، تأسیسات | صف درخواست‌های واحد خود |
| مدیر محتوا | روابط عمومی، دفتر پرستاری | انتشار اخبار و بخشنامه، هدف‌گذاری مخاطب |
| مسئول آموزش / مدرس | واحد آموزش | دوره، محتوا و آزمون (فاز ۶) |
| مسئول پژوهش | واحد توسعه تحقیقات بالینی | فراخوان‌ها و طرح‌ها (فاز ۶) |
| مدیر ارشد | ریاست، مدیریت | داشبوردها و گزارش‌های تجمیعی (بدون هویت گزارش‌دهنده) |
| حسابرس | حراست/فناوری اطلاعات | فقط خواندن لاگ‌های حسابرسی |
| مدیر سیستم | تیم فنی | کاربران، نقش‌ها، تنظیمات؛ **بدون** دسترسی خودکار به محتوای گزارش‌های خطا |

**محرمانگی گزارش‌دهنده:** گزارش ناشناس هیچ پیوندی به کاربر در پایگاه داده ندارد؛ پیگیری با «کد پیگیری + رمز» انجام می‌شود. در گزارش غیرناشناس، هویت گزارش‌دهنده فقط برای کارشناس ایمنی بیمار قابل مشاهده است و در داشبوردها و برای مسئول واحد پنهان می‌ماند. قاعده دقیق باید با سیاست بیمارستان تطبیق داده شود (پرسش ۵).

## ۴. نیازمندی‌های کارکردی

برچسب فاز: **M** = نسخه MVP، **P5** = فاز خدمات عمومی، **P6** = فاز تکمیلی، **P?** = منوط به مجوز.

### ۴.۱ هسته (ورود، کاربران، نقش‌ها)
- M: ورود کارکنان با کد پرسنلی + رمز عبور؛ قفل موقت پس از تلاش‌های ناموفق؛ تغییر رمز اجباری در اولین ورود
- M: مدیریت کاربران، واحدها (ساختار درختی)، نقش‌ها و مجوزها در پنل
- M: ثبت لاگ حسابرسی
- P6: ورود دومرحله‌ای (TOTP یا پیامک) برای نقش‌های حساس
- P?: ورود یکپارچه با Active Directory/LDAP اگر بیمارستان دارد (پرسش ۲)
- P5: ثبت‌نام مراجعان با شماره موبایل و OTP پیامکی (نیاز به سرویس پیامک، پرسش ۶)

### ۴.۲ گزارش خطا و ایمنی بیمار
- M: ثبت خطا، حادثه (عارضه ناخواسته)، شبه‌خطا (near miss) و مشکل تجهیزات با فرم شرطی (فقط سؤال‌های مرتبط با نوع انتخاب‌شده نمایش داده شوند)
- M: انتقال فهرست ~۳۴ سؤال فرم فعلی (`khata.kt`) به قالب فرم پویا
- M: گزارش ناشناس یا با نام؛ کد پیگیری
- M: پیوست عکس/فایل (با محدودیت نوع و حجم)
- M: گردش کار: ثبت‌شده → بررسی اولیه → ارجاع به واحد/مسئول → در حال اقدام → اقدام اصلاحی ثبت‌شده → بسته‌شده (با تاریخچه وضعیت)
- M: ثبت اقدام اصلاحی با مسئول و مهلت
- M: ذخیره آفلاین و ارسال خودکار پس از اتصال
- M: آمار پایه: تعداد بر اساس نوع، واحد، شدت، ماه؛ میانگین زمان رسیدگی
- P6: تحلیل ریشه‌ای (RCA)، خروجی Excel/PDF، طبقه‌بندی مطابق فهرست وقایع ناخواسته وزارت بهداشت (پرسش ۵)

### ۴.۳ اطلاع‌رسانی سازمانی
- M: انتشار خبر، بخشنامه و دستورالعمل با دسته‌بندی و پیوست PDF
- M: هدف‌گذاری مخاطب: عمومی، همه کارکنان، نقش خاص، واحد خاص
- M: آرشیو و جستجو
- M: «تأیید مطالعه» برای اطلاعیه‌های مهم و گزارش اینکه چه کسانی نخوانده‌اند
- M: اعلان درون‌برنامه‌ای؛ P?: Push Notification (پرسش ۷)
- P6: زمان‌بندی انتشار، تاریخ انقضا، گردش تأیید پیش از انتشار

### ۴.۴ خدمات اداری و پشتیبانی
- M: ثبت درخواست فناوری اطلاعات، تجهیزات و تأسیسات
- M: «نوع درخواست» قابل تعریف در پنل (با فرم پویا و واحد مسئول پیش‌فرض)
- M: ارجاع، تغییر وضعیت، ثبت اقدام، نتیجه نهایی، امتیاز رضایت درخواست‌کننده
- P6: SLA (مهلت رسیدگی) و هشدار تأخیر، درخواست‌های اداری چندمرحله‌ای (مثلاً مرخصی) در صورت نیاز

### ۴.۵ خدمات بیماران و مراجعان
- M (حداقلی): راهنمای بخش‌ها و درمانگاه‌ها، پرسش‌های متداول، ثبت پیشنهاد/انتقاد/شکایت با کد پیگیری، اطلاعیه‌های عمومی
- P5: فرایند مراجعه و مدارک لازم برای هر خدمت، نظرسنجی رضایت، درخواست راهنمایی (پرسش‌وپاسخ)، حساب کاربری مراجع
- P?: نوبت‌دهی و مشاهده اطلاعات بیمار، فقط پس از بررسی HIS و مجوز (پرسش ۱)

### ۴.۶ آموزش (P6)
- دوره، فصل، محتوا (متن، PDF، ویدئو)، ثبت‌نام و تکلیف دوره برای نقش/واحد
- آزمون با بانک سؤال، زمان‌بندی، نمره قبولی، تصادفی‌سازی
- پیشرفت و سوابق آموزشی، گواهی
- گزارش برای مسئول آموزش

### ۴.۷ پژوهش و نوآوری (P6)
- فراخوان‌ها و رویدادهای علمی
- ثبت ایده و پیشنهاد پژوهشی، داوری و پیگیری وضعیت
- منابع و دستورالعمل‌ها (کتابخانه فایل)

### ۴.۸ گفتگوی داخلی (P6)
- گفتگوی دونفره و گروهی، کانال واحدها، ارسال فایل مجاز، اعلان پیام
- تصمیم لازم: ساخت درون سامانه یا استقرار یک پیام‌رسان متن‌باز روی سرور بیمارستان (پرسش ۱۴). ساخت پیام‌رسان امن از نو پرهزینه‌ترین ماژول است.

### ۴.۹ مدیریت و تحلیل
- M: داشبورد پایه (گزارش‌های خطا و درخواست‌ها: تعداد، روند، زمان رسیدگی، واحدهای پرتکرار)
- P6: شاخص‌های عملکرد قابل تعریف، گزارش‌های دوره‌ای، خروجی فایل، فیلتر بر اساس سطح دسترسی

### ۶.۵ اعلان‌ها
MVP: اعلان درون‌برنامه‌ای (جدول `notifications` + دریافت هنگام باز شدن اپ + WorkManager دوره‌ای). بعد: WebSocket برای پیام فوری. FCM در ایران و روی گوشی‌های بدون سرویس گوگل قابل اتکا نیست؛ گزینه‌های جایگزین (سرویس‌های Push داخلی یا اتصال دائمی خودمیزبان) باید از نظر امنیتی تأیید شوند (پرسش ۷).

## ۷. مدل داده (هسته MVP)

همه جدول‌ها: `id` (UUID)، `created_at`، `updated_at`؛ حذف منطقی (`deleted_at`) برای داده‌های قابل حسابرسی.

**هسته**
- `units` (id, name, parent_id, type: بخش/درمانگاه/واحد پشتیبانی, is_public)
- `users` (personnel_code, national_id_hash, full_name, mobile, password_hash, is_active, must_change_password, last_login_at, failed_attempts, locked_until)
- `roles` (code, name)، `permissions` (code)، `role_permissions`
- `user_roles` (user_id, role_id, unit_id nullable ← دامنه)
- `refresh_tokens` (user_id, token_hash, expires_at, revoked_at, device_info)

| مرحله | محتوا | معیار پذیرش (قابل آزمون) |
|---|---|---|
| **۰. آماده‌سازی** | ساختار monorepo، حذف APK از git، CLAUDE.md، SessionStart hook، CI (Android build + unit test، backend pytest، admin build) | CI روی PR سبز؛ اپ فعلی در CI build می‌شود |

## ۱۴. آماده‌سازی محیط توسعه

1. **شبکه محیط ابری:** فقط `dl.google.com` بسته است (PyPI، npm، Maven Central، Google Maven، Gradle و Docker Hub در این جلسه پاسخ دادند). این پروژه هنوز محیط ابری اختصاصی ندارد و روی محیط پیش‌فرض بدون تنظیمات اجرا می‌شود. مسیر: Project settings ← Cloud environment ← Add cloud environment ← Network access: سطح Limited، دامنه `dl.google.com` در Allowed domains، گزینه Allow package managers تیک‌خورده بماند. راهنما: https://code.claude.com/docs/en/cloud-environments#network-access
2. **CLAUDE.md در مخزن:** مفید است و در مرحله ۰ می‌نویسم: دستورهای build و تست هر بخش، قواعد (فارسی/RTL، عدم ثبت داده بیمار در لاگ، commit نکردن APK، بدون ادعای تست‌نشده)، نقشه ماژول‌ها.
3. **SessionStart hook:** مفید است، چون هر جلسه ابری از صفر شروع می‌شود. اسکریپت `.claude/hooks/session-start.sh` در مخزن: نصب Android SDK (پس از باز شدن `dl.google.com`)، نصب وابستگی‌های Python و Node، راه‌اندازی PostgreSQL برای تست. JDK 21، Python 3.13، Docker و psql همین الان در محیط هستند.
4. **CI در GitHub Actions:** ضروری است؛ حتی بدون باز شدن `dl.google.com` اپ را در CI build و تست می‌کند. سه job: Android (assemble + unit test + lint)، backend (pytest با سرویس PostgreSQL)، admin-web (build + test). توجه: در مخزن خصوصی، دقیقه‌های رایگان Actions محدود است.
5. **اسکیل و پلاگین:** نصب چیز جدیدی لازم نیست. ابزارهای موجود که استفاده می‌کنم: `security-review` برای بازبینی امنیتی هر PR که به ورود، دسترسی یا داده بیمار دست می‌زند؛ `code-review` برای بازبینی کیفیت؛ `session-start-hook` برای ساخت hook مرحله ۰؛ Playwright (از پیش نصب) برای تست پنل وب. بعد از اینکه الگوی ماژول‌ها ثابت شد، یک اسکیل اختصاصی پروژه («افزودن ماژول جدید») می‌تواند تکرار کار را کم کند.
